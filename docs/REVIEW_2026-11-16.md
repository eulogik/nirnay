## 2. Why nobody uses it yet

The model is good. The funnel is broken.

1. **`pip install nirnay` installs someone else's package.** Our name was
   free on 2026-09-30; Dobbyisus published `nirnay` on 2026-10-02. We
   cannot ship under that name. This alone blocks a one-line install.
2. **No one-line API.** A new user must find a 466MB checkpoint, know
   `NirnayAgent`, pass a checkpoint path, and build the criteria dict.
   There is no `classify(text, labels)`.
3. **No classify CLI.** Only `nirnay-train` (full pipeline) and
   `nirnay-server`. Nothing a normal user can type in one line.
4. **Server defaults to the wrong model.** `nirnay-server` with no env
   loads raw Laya, not the trained checkpoint. Confusing and wrong.
5. **The demo cold-starts with a 1.3GB download.** First visitor waits
   minutes. The Space repo ships code only.
6. **Slow for the "inline routing" story.** 361ms CPU for 77-way,
   86-108ms for 10 labels. Laya is 33ms, Clef-Flash 38.8ms. ONNX gave
   no speedup.
7. **No custom-label workflow.** The zero-shot custom-label result is
   strong, but it is undocumented and there is no way to fine-tune on a
   user's own labels without running the full Phase A/B CLI.
8. **Research voice.** README leads with architecture and ablation
   details, not with "what can I do with this in five minutes".

## 3. The v0.2 breakthrough: "your labels, in one line, on your machine"

North star: **from zero to a correct custom-label decision in under two
minutes**, and **under 150ms per decision on CPU for 10-30 labels**.

The product changes from "a Banking77 model" to "a local calibrated
classifier where you bring the labels". Banking77 stays as the proof
benchmark, not the product.

### Workstream A: package, API, CLI (2 days)

* Rename the distribution to **`nirnay-450m`** and the import to
  **`nirnay_450m`**. The name `nirnay` is taken and colliding at the
  import level is a landmine. All alternatives checked free
  (`nirnay-450m`, `eulogik-nirnay`, `nirnay-decision`).
* High-level API:
  ```python
  from nirnay_450m import Classifier
  clf = Classifier()  # auto-downloads weights, CPU by default
  result = clf("My card was charged twice", {
      "duplicate_charge": "charged twice",
      "refund_status": "asking about a refund",
  })
  # result.choice, result.probabilities, result.confidence
  ```
* CLI:
  ```bash
  nirnay classify "text" --labels labels.json
  nirnay classify --input data.jsonl --output results.jsonl --labels labels.json
  nirnay serve --port 8000   # Jev-compatible /v1/systemone
  nirnay fit --data train.jsonl --labels labels.json --out my_model   # week 2
  ```
* `nirnay serve` defaults to the shipped checkpoint, auto-downloads it,
  and exposes the same wire format as Jev.
* Auto-download with a cache, progress bar, and a clear error if offline.
* Publish to PyPI under `nirnay-450m` after `twine check`.

Acceptance: fresh venv, `pip install nirnay-450m`, `nirnay classify`,
result in under two minutes including download. Warm decision under 2s.

### Workstream B: speed (2 days, uncertain)

* Try ONNX dynamic int8 and ORT thread tuning. Target 77-way CPU under
  200ms and 10-label under 60ms. If int8 fails parity, ship the current
  ONNX as a portability path and stop claiming speed.
* Add synchronous batch mode. Batching is the one guaranteed win for
  offline workloads.
* Publish a measured latency table by label count, CPU/GPU.

Acceptance: measured, not estimated; keep only the numbers that reproduce.

### Workstream C: custom labels + light fine-tune (3-4 days)

* Document zero-shot custom labels (proven: 0.8833 with neutral keys on
  in-domain data). Add a `labels.json` format and a `--labels` flag.
* `nirnay fit`: load `phase_b`, freeze the encoder, train only the
  scorer/head on the user's labels, fit temperatures, save a small
  adapter/checkpoint. This is the difference between a demo and a tool.
* Test on a truly out-of-domain set before promising it. If zero-shot
  OOD is weak, say "in-domain or fine-tune" in the docs.

Acceptance: a user's 20-label dataset fine-tunes on a Mac/Colab in
under 30 minutes and beats the zero-shot path on held-out rows.

### Workstream D: deployment (1-2 days)

* Space cold start: bake `phase_b.pt` into the Space repo (466MB) so it
  is part of the image, and replace the runtime Laya download with a
  local copy or a persistent cache. Target first prediction under 60s.
* Add a Dockerfile and `docker run` one-liner for the server.
* Keep the free ZeroGPU Space; do not add paid infrastructure.

Acceptance: wake the Space, first prediction under 60s; Docker image
serves `/v1/systemone` with the trained checkpoint by default.

### Workstream E: relaunch (2 days)

* New README first screen: "bring your labels, get calibrated answers,
  local, 450M". Banking77 as proof. Five-minute quickstart. Latency
  table. Limits.
* New launch angle: "Jev-compatible, open weights, your labels".
  This is a different story from the first launch and it is true.
* Relaunch on HN (one retry allowed with real news), Reddit, X,
  LinkedIn, Dev.to. Space demo first in every post.
* Do not submit to JevBench. Do not promise GGUF.

## 4. What not to do

* GGUF/Ollama before A-C. It is distribution, not usability, and it
  needs C++ graph work for four custom heads on an unmerged upstream PR.
* JevBench submission at current intelligence (~0.55 public).
* Long-context research for v0.2. It is a v1.1 topic.
* More benchmark rows. The model is measured enough.

## 5. Sequencing

Week 1: A + B + D. First usable package, CLI, server, faster demo.
Week 2: C + E. Custom labels, light fine-tune, docs, relaunch.

The single highest-leverage change is A: without a working package name
and a one-line call, nothing else matters.

## 7. Workstream B result

Dynamic int8 was tested and rejected. It cut the artifact to 561MB and
ran faster (359ms vs 542ms float in the same process) but agreed with
the float model on only 20 of 24 decisions, with max logit delta 9.79.
For a calibrated classifier that is a fail, not a tradeoff. Report in
`eval/onnx_int8_report.json`. ONNX remains a portability path.
